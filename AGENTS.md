# AGENTS.md

## Repository Shape
- This is a **Bun** workspace (`packageManager: bun@1.4.5`); install with `bun install --frozen-lockfile` to match CI. Bun `>=1.4.0` is required for both the package manager and the `ponder` runtime. CI pins runner images (`ubuntu-24.04`, `windows-2025`), uses the Postgres preinstalled on the runner (16 on Linux, 17 on Windows), and sets up Bun and Foundry versions inline in each workflow job. Repo settings require every third-party action to be pinned to a full-length commit SHA (with the version tag in a trailing comment).
- Workspace packages are `packages/*` only (see root `package.json` `workspaces`). `examples/`, `docs/`, `simulation-test/`, and `benchmark/` are **not** workspace packages — install inside those directories when needed (`bun install` in that directory; they use `file:` deps into `packages/*`).
- `packages/core` publishes the `ponder` npm package. Public exports start in `packages/core/src/index.ts`; the CLI bin starts in `packages/core/src/bin/ponder.ts`.
- `packages/core` and `packages/react` build with custom `build.ts` scripts. `packages/client`, `packages/utils`, and `packages/create-bponder` build with tsup.
- Core source uses `@/*` path aliases. The core build rewrites these aliases in `dist/esm` and `dist/types`, so do not replace source aliases just to satisfy package output.

## Commands
- Build publishable packages: `bun run build`.
- Lint and format use Biome: `bun run lint`, `bun run format`, `bun run lint:fix`.
- Root typecheck covers `packages/**` only: `bun run typecheck`.
- Focused package checks: `bun run --cwd packages/core typecheck`, `bun run --cwd packages/client typecheck`, `bun run --cwd packages/utils typecheck`, `bun run --cwd packages/create-bponder typecheck`.
- Focused tests: `CI=1 bun test packages/core/src/path.test.ts`, `CI=1 bun run --cwd packages/client test src/index.test.ts`, `bun run --cwd packages/create-bponder test`.
- Type-level Vitest suites use separate scripts where present: `bun run --cwd packages/core test:typecheck`, `bun run --cwd packages/client test:typecheck`, `bun run --cwd packages/react test:typecheck`.
- Prefer `bun run --cwd <pkg>` over `bun run --filter` in CI/scripts: Bun 1.4.x on Linux can abort `--filter` with bare `FileNotFound` when a workspace glob points at a missing path (e.g. former `tmp/*`). Set `CI=1` for one-shot local Vitest runs.

## Tests And Environment
- Core Vitest setup (`packages/core/vite.config.ts`) caps threads at 4, loads `packages/core/src/_test/setup.ts`, and runs `packages/core/src/_test/globalSetup.ts`.
- Core global setup requires committed `packages/core/src/_test/generated.ts` (regenerate with `bunx @wagmi/cli generate` in `packages/core` after contract changes), then starts an Anvil proxy. Foundry/Anvil must be installed for core tests.
- Core database tests default to in-memory PGlite. Set `DATABASE_URL` in `packages/core/.env.local` only when intentionally testing Postgres; tests create and drop `vitest_*` databases/roles.
- `packages/utils/src/_test/*` contains live RPC-provider tests that require `RPC_URL_*` values from `packages/utils/.env.example`; avoid broad utils/root test runs unless those env vars and network access are intended.
- `simulation-test` and `benchmark` are outside the workspace; run `bun install` in each directory after `bun run build`. They use Bun scripts and external Postgres/RPC env from their `.env.example` files. Their `DATABASE_URL` should omit a database name; scripts append app-specific database names.
- `simulation-test` fault injection needs `PONDER_USE_VITE=1` and typically `PONDER_DATABASE_DRIVER=pg` (`onBuild` is Vite-path only; see `docs/guides/bun.md`).

## Memory Profiling
- Profile memory while running an example app, such as `feature-multichain`. Run it for several minutes so finalization occurs; temporarily comment out chains when necessary to keep the workload practical.
- Expose V8 garbage collection with `NODE_OPTIONS=--expose-gc`. Call `global.gc()` immediately before every reading so the measurement compares retained objects rather than differences in GC timing.
- Print `process.memoryUsage()` values for `rss`, `heapUsed`, `heapTotal`, and `external`, plus `v8.getHeapStatistics().heap_size_limit`. Report values in MiB, for example: `[memory] rss=...MiB heapUsed=...MiB heapTotal=...MiB heapLimit=...MiB external=...MiB`.
- Keep profiling code temporary and rebuild `packages/core` after removing it so ignored `dist/` artifacts do not retain stale instrumentation. Never commit RPC or database credentials from local profiling environments.

## Generated Or Copied Files
- `packages/core/src/_test/generated.ts` is generated by Wagmi from Foundry contracts under `packages/core/src/_test/contracts/` and is ignored by Biome.
- `packages/create-bponder` build copies root `examples/` into `packages/create-bponder/templates`, excludes multi-app examples (`with-solidstart`, `with-foundry`, `with-trpc`, `with-client`, `with-offchain`), renames dotfiles, and blanks RPC URLs in generated `_dot_env.local` files.
- Biome intentionally ignores `docs/`, `dist/`, generated folders, `.ponder`, cache/out directories, Solidity files, and `bun.lock`.

## Docs, Examples, Releases
- Docs live as plain Markdown under `docs/` (see `docs/README.md`). There is no Vocs / docs site build.
- CI separately verifies the SolidStart frontend example with `bun run --cwd examples/with-solidstart/frontend build` after `bun run build`.

## Changesets
- Changesets are fixed for `bponder`, `create-bponder`, `bponder-client`, and `bponder-react`; docs/examples are ignored. Create changesets with `bunx changeset`. Public API or bug-fix PRs normally need a patch changeset.
- Write changesets in the same voice as `packages/core/CHANGELOG.md`: concise, user-facing, past tense, and focused on observable behavior.
- Start with the outcome, not the implementation. Prefer phrasing like "Fixed a bug that caused...", "Fixed a regression introduced in `v0.16.0` that caused...", "Improved...", "Added...", "Updated...", or "Removed...".
- Include concrete symptoms when helpful, especially exact error messages in backticks. Use patterns like "Fixed the error `...`" or "that caused `...`".
- Name affected APIs, config fields, commands, packages, and options with backticks, such as `ponder.config.ts`, `context.client`, `context.db`, `bponder-client`, `p.bytes()`, `ordering: "omnichain"`, and `bponder db list`.
- Use repository vocabulary consistently: Ponder, GraphQL, JSON-RPC, RPC, Postgres, PGlite, backfill, live, crash recovery, factory, and rpc cache.
- Avoid implementation details, internal refactors, PR narration, and vague language unless the detail explains user impact. Do not write "this PR", "we", "users may notice", "various fixes", or "some improvements".
- Keep each changeset entry narrow. If a PR includes unrelated user-facing changes, use multiple changesets or multiple short paragraphs so each changelog bullet is easy to scan.
- For dependency-only updates, only write a custom changeset if there is a user-facing reason, such as a security patch or a fixed runtime error.
